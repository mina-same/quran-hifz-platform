## User Preferences

## Key Learnings
- **`xcodebuild` error 65 / "Script '[Expo] Configure project' failed" is a generic wrapper, not the cause.** Always scroll the log for the real line — on 2026-08-30 it was `LLVM ERROR: IO failure on output stream: No space left on device` (disk 100% full). The trailing warnings expo prints (ambiguous script dependencies on '[Expo Dev Launcher] Strip Local Network Keys', `SDWebImage iOS@9.0 deployment version mismatch`) are cosmetic and appear on EVERY build — never chase them. First move on an error-65: `df -h /System/Volumes/Data`, then `rm -rf ~/Library/Developer/Xcode/DerivedData/*`.
- **Terminology moved on: they are `المسارات`, not `المسارات الاستثنائية`.** The API route/type is still `special-tracks`/`SpecialTrack`, but every user-facing label follows the web: `المسارات` (admin) / `مساراتي` (student, teacher). Also structural: a حلقة now REQUIRES a مسار (`specialTrack` is a required field on the halqa form), so a halqa is a child of a programme, not a parallel concept.
- **Mobile has no filesystem download.** CSV export goes through `lib/csv.ts` → `shareCsv()` → RN's `Share` sheet with the CSV as the message body. A real .csv attachment needs expo-file-system + expo-sharing, which are NOT installed (adding them means a dev-client rebuild).
- **The admin CRUD screens share:** `FormPage` (full-screen add/edit route container), `ConfirmDialog` (destructive confirm), `CredentialsDialog` (one-time account display) and `IconButton` (row actions). Reuse them rather than hand-rolling another modal.
- **`theme.textFaint` / `theme.textLight` are white ink, in BOTH modes** (`rgba(255,255,255,…)` in `lightSurfaces` too). They exist for text on a green/dark fill — the lock screen, a header band. On a card they are invisible in light mode. For a de-emphasised line on a card use `theme.textMuted` (optionally with `opacity`).
- **Icons: `@tabler/icons-react-native` is installed and mirrors the web's `ti-*` names** (`ti-calendar-off` → `IconCalendarOff`). Porting a web screen's icons is a mechanical rename; check `node_modules/@tabler/icons-react-native/dist/tabler-icons-react-native.d.ts` for the exact export.
- **Nested `Pressable`s don't bubble in RN**, so a card whose whole body navigates will still let inner buttons work — but any *inert* region inside it (an expanded inline panel, a form) becomes a navigation trap. Keep such panels outside the navigating Pressable.
- **Mobile theming has exactly one legal shape.** `lib/theme.ts` deliberately exports NO module-level `theme` object — only `buildTheme(mode)`, the `Theme` type, and the RTL constants `textStart`/`textEnd`. Read colours through `useAppTheme()` (which returns the built theme plus `mode`) and build the sheet inside the component: `const styles = useMemo(() => createStyles(theme), [theme])`, with `createStyles(theme: AppTheme)` at the bottom of the file. A module-scope `StyleSheet.create({...})` that reads theme colours runs once at import and freezes whichever mode loaded first — that is a dark-mode bug, not a style preference. A module-scope sheet holding ONLY layout (flex/gap/width) is still fine.
- **`theme.green` (#1B5E20) is nearly black.** It works as ink on light and as a deliberately-deep full-screen brand background (BiometricLockScreen), but it disappears both as a fill and as ink on a dark surface. Use `theme.greenAccent` (green in light, greenLight in dark) anywhere green must read against the page: filled chips, primary buttons, active tab labels, progress fills, card header bands.
- **`theme.white` is ink, not a surface.** It is mode-independent on purpose — white text on a coloured fill. A white *surface* is `theme.card` (raised), `theme.bg` (page/recessed), `theme.cardAlt` (inset panel, table header) or `theme.inputBg` (form field fill). Writing `backgroundColor: theme.white` is how the tab bars and half the domain cards stayed white in dark mode.
- **Status colours come from `theme.tone[green|gold|red|blue|gray]`** — a `{bg, border, text}` triple defined per mode and shared by Badge, Alert, DataTable and every status chip. Never inline a Tailwind pastel (`#DCFCE7`, `#F0FDF4`) as a background; a pastel is a light-mode surface, and the dark counterpart is a desaturated near-black wash with the light hue moved onto the *text*, not the same pastel dimmed.
- Cards drop their shadow in dark mode and use a hairline `theme.border` instead — a drop shadow reads as nothing against a near-black page.
- @gorhom/bottom-sheet LOCKS its scrollable whenever the sheet is not at its HIGHEST snap point: `useScrollEventsHandlersDefault` calls `scrollTo(0, lockPosition)` on every onScroll/onEndDrag/onMomentumEnd while SCROLLABLE_STATUS is LOCKED. So ANY sheet holding a scrollable list must use a SINGLE snap point — multi-snap (e.g. ['50%','80%']) makes the list snap back to where the drag started, which users report as "it goes back to the start". Applies to BottomSheetFlatList/ScrollView alike.
- BottomSheetFlatList's TYPES omit `onScroll`/`scrollEventThrottle`/`decelerationRate`, but the runtime does forward a provided `onScroll` (via runOnJS inside useScrollHandler). Rather than cast, use `onViewableItemsChanged` + `viewabilityConfig` for per-row work — it passes straight through `...rest` and costs no per-frame JS bridge hop.
- The mobile app has no Expo-template SafeAreaProvider by default — it was added to app/_layout.tsx on 2026-08-28. `SafeAreaView` from react-native-safe-area-context works without it (native view), but `useSafeAreaInsets()` THROWS. Check the provider is present before adding the hook anywhere.
- The shared BottomSheet (components/ui/BottomSheet.tsx) now pays the bottom safe-area inset itself, so sheet content must NOT add its own home-indicator padding.
- `<Alert>` (components/ui/Alert.tsx) now wraps text-only children itself, but the general RN rule still applies: any JSX with an interpolation is an ARRAY of children, so a component that special-cases `typeof children === 'string'` will crash with "Text strings must be rendered within a <Text> component". Check that when adding children-based components.
- Mobile `hydrate()` restores a session WITHOUT navigating, so the (portal) group's first registered screen is where every role lands on resume. Any role→portal routing must be enforced in app/(portal)/_layout.tsx (pathname vs authUser.role), not assumed from login-time navigation.
- Read-only DB audits are easy: copy a script into quran-hifz-server/ (so `mongoose` resolves), read MONGO_URI out of its .env, and run it with node. Confirmed 0 dangling User.profileId values as of 2026-08-28.
- The server's POST /evaluations/bulk is the single save path for "الحضور والتقييم": evaluation.controller.ts also calls upsertAttendanceRecords() and notifyParents(), so saving an evaluation writes the Attendance doc and pushes absence notices. Do NOT call /attendance/bulk separately from that screen.
- Mobile mirrors web rubric constants in lib/evaluationRubric.ts (حضور 3 + حفظ 4 + تجويد 2 + تلاوة 1 = 10) — no shared package between the two npm projects; same convention as surahs.ts/juz.ts.
- NativeWind is active on EVERY element here (babel `jsxImportSource: 'nativewind'`), and on native its interop drops `style={({ pressed }) => [...]}` function styles — the view renders with no background at all. Always pass a plain style array; track pressed with onPressIn/onPressOut. Web builds do NOT reproduce this (NativeWind emits real CSS there). Still-suspect files with the same pattern: components/layout/NavItem.tsx, components/layout/MoreSheet.tsx, components/domain/MasjidAccordion.tsx, app/(portal)/student/messages.tsx, app/index.tsx (child cards).
- Don't use `android_ripple` on a rounded Pressable in this app: on Android it replaces the background with a square-masked RippleDrawable, which can hide the fill (white label on no fill = invisible button) and break the rounded corners. Use pressed opacity + `overflow:'hidden'` instead; keep shadows iOS-only.
- Expo web (`npx expo start --web`) + Playwright is a working way to screenshot this app, but it will NOT reproduce Android-only rendering bugs.
- Mobile app already has NativeWind v4 + tailwind.config.js + global.css wired, but the UI is written with StyleSheet + `useAppTheme()`; react-native-reusables (shadcn for RN) would be a real migration (cva/clsx/tailwind-merge/rn-primitives + CSS-var theme + ~16 Button call sites), not a drop-in.
- User dislikes ad-hoc `style={{padding/radius}}` overrides on Button — put sizing in the Button's own size scale instead.
- Mobile app forces RTL (`I18nManager.forceRTL(true)` in `app/_layout.tsx`), so flex `flex-start` = visual RIGHT and `flex-end` = visual LEFT. To place a control at the visual left corner (e.g. the login gear button), use `alignItems: 'flex-end'`.
- Backend has no forgot-password or magic-link endpoints — don't add those UI controls to login screens.

- [2026-07-10] **Mongoose gotcha, bit twice in one session:** spreading a Mongoose subdocument directly (`{ ...s }` where `s` came from `plan.schedule` / any `[SubSchema]` array field on a fetched document) does NOT give you a plain object — it copies internal Mongoose instance properties (`__parentArray`, `$__`, `_doc`, etc.) instead of the actual field values, and any `required` field then reads as `undefined` on save (triggers `ValidatorError: Path 'x' is required` even though the source document clearly had that field populated). Always call `.toObject()` on the parent document first (`plan.toObject().schedule.map(...)`), matching the existing convention already used in `quran-plan.controller.ts`'s `withTodayAssignment` — never `doc.subArray.map((s) => ({...s}))` directly off a live Mongoose doc. Hit this in both `student-plan-progress.controller.ts`'s `getStudentProgress` (silent data corruption — leaked Mongoose internals into the JSON API response) and `studentPlanReflow.ts`'s `initStudentOccurrences` (hard 500 on the very first `record` call). If `npx tsc` prints "This is not the tsc command you are looking for", `node_modules` is missing and npx fell through to a global stub; check `ls node_modules` before believing a clean typecheck.

To place something visually left, give it a higher `order` — do not reorder the DOM, which also controls the mobile stacking order.

- **A QuranPlan holds one segment per type** (`segments[]`: type + days + rangeStart/rangeEnd + schedule). The plan's window — startDate, endType/endDate/activeDaysCount, holidays, target, teacher — is SHARED by every segment. Legacy single-type documents keep their old top-level fields and are migrated **on read** by `normalizePlanSegments()` (server) / `segmentsOf()` (reflow); never rewrite them in place.
- **The weekdays are partitioned: no date belongs to two types.** Enforced by `validateSegmentDays()` (shared verbatim across all three codebases). - **`occurrenceIndex` is 1-based WITHIN a segment.** A day is addressed by the pair `(type, occurrenceIndex)` — an index alone is no longer unique. Applies to `plan.segments[].schedule`, `StudentPlanProgress.occurrences`, and every record/edit endpoint.

- **Direction is per segment**, not per plan — مراجعة may run forward while حفظ runs backward. Read it via `segmentReversed(plan, type)`, never `isReversedRange(plan.rangeStart, ...)` (those fields no longer exist on the client `QuranPlan` type, deliberately, so the compiler catches it).

### Plan schedule dates are LOCAL midnight, serialized as UTC ISO (2026-08-28)
`computeScheduleBreakdown` walks a `dateOnly()` cursor (local calendar fields) but emits
`date: cursor.toISOString()`. Never read those back with `.split("T")[0]` — that's the UTC
day and drifts back one day in any timezone ahead of UTC (Cairo is +2/+3). Parse and read
local fields instead. Same reason plan `holidays` are stored as plain `YYYY-MM-DD` strings,
not `Date`s: a holiday is a calendar day, and a Date re-introduces the shift on every read.

### The scheduling engine is duplicated in THREE places (2026-08-28)
`quran-hifz-server/src/lib/quranRange.ts`, `quran-hifz/src/quran/lib/quranRange.ts`, and
`quran-hifz-mobile/lib/quranRange.ts` — web and mobile compute the schedule live client-side
for form previews, so any engine change must be applied to all three or the preview silently
disagrees with what the server saves. The two client copies are a subset: they have
`countMatchingDays`/`countOccurrences`/`computeScheduleBreakdown` but NOT
`computeTodayAssignment`/`computePlanProgress`. Only the mobile copy has tests
(`quran-hifz-mobile/lib/quranRange.test.ts`, run with `npx jest`).

### Buttons use `.topbar-btn` as the base class, everywhere (2026-08-28)
`quran.css` defines NO `.btn` class. `.btn-primary`, `.btn-ghost`, `.btn-danger`, `.btn-gold`
are colour modifiers with no layout of their own — padding/radius/font/flex all sit on
`.topbar-btn`, which despite its name is the base class for every button in the app,
including form buttons. Writing `className="btn btn-ghost"` yields an unstyled button.
Always: `className="topbar-btn btn-primary"`.

### @gorhom/bottom-sheet v5 — BottomSheetView collapses flex children (2026-08-28)
`BottomSheetView` merges its style as `[callerStyle, {position:'absolute',top:0,left:0,right:0}]`,
so it hugs content height and any `flex: 1` child renders at height 0 — the sheet opens but looks empty.
With fixed `snapPoints`, pass `bottom: 0` (the one edge the library never overwrites) to make it fill.
Never do this when `enableDynamicSizing` is on — the sheet height is derived from this view's measured height.

### Never call BottomSheetModal.dismiss() before present() (2026-08-28)
In a controlled `visible` wrapper around @gorhom/bottom-sheet v5, an `else dismiss()` branch fires on first mount
and permanently pins the modal's internal status at `DISMISSING` (forceClose() hits a null inner-sheet ref, so no
callback ever clears it). `handlePortalRender` then refuses to render forever — present() silently does nothing.
Guard with a `wasPresented` ref, and clear it in `onDismiss` too since the library resets to INITIAL on unmount.

### RTL text alignment — `textAlign: 'right'` renders visually LEFT (2026-08-28)
The app forces RTL (`I18nManager.forceRTL(true)` in app/_layout.tsx), and RN then **swaps left/right text
alignment**: `effectiveParagraphStyle` in node_modules/react-native/Libraries/Text/RCTTextAttributes.mm turns
NSTextAlignmentRight into NSTextAlignmentLeft whenever the view's layout direction is RTL. So on a <Text>,
`textAlign: 'right'` puts Arabic on the visual LEFT, and an unset alignment resolves left too. `<TextInput>`
does NOT get the swap (FormInput/FormTextarea/FormSelect's search field keep `textAlign: 'right'` and are
correct). This is why input labels, DataTable cells and every bottom-sheet header sat on the left.
**Fix:** `components/ui/Text.tsx` wraps RN's <Text> and applies `textStart` to all of it; import Text from
'@/components/ui/Text', never from 'react-native'. `textStart` (= 'left', visually right) and `textEnd`
(= 'right', visually left) are exported from lib/theme.ts — use those tokens, never a bare literal.
Note `I18nManager.swapLeftAndRightInRTL(false)` does NOT help: it governs Yoga layout props, while the text
swap keys off the view's layout direction independently.
